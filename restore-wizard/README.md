# Stocksite Restore Wizard

The generated helper archive is a setup-only bundle containing this guide, `restore-wizard.html`, `restore-manifest.json`, and the helper's `.env.example`, Node entry point, lockfile/package manifest, and Windows/macOS launch scripts. Dependencies are installed from the included lockfile with `npm ci --ignore-scripts`; no development-machine `node_modules` or test files are bundled. The database backup and three data ZIPs are separate package downloads, not copies embedded in the helper ZIP. Use the helper on the Developer computer or the new Windows/macOS restore target. The helper runs as the signed-in local user and does not elevate privileges; the SERVER never executes commands on that computer.

## SERVER package-generation configuration

The existing `?tab=restore` page sends its authenticated START request through the configured Developer-to-SERVER connection and uses the existing verified Backup Center collection pipeline. Starting a package requires an explicit admin-only consent checkbox because the encrypted website `.env` payloads may contain production secrets. Restore packages and their private job state are retained for up to 24 hours, then removed by the package cleanup path. The SERVER must already have:

- `DB_HOST` (or `PGHOST`) and `DB_NAME` (or `PGDATABASE`), a working database pool, and compatible `pg_dump`/`pg_restore` executables. Configure `PG_DUMP_PATH` and `PG_RESTORE_PATH` when they are not on PATH.
- `BACKUP_ENCRYPTION_KEY` to encrypt website `.env` payloads before staging.
- Absolute, non-overlapping `ASSETS_ROOT` and `THUMBNAIL_STORAGE_PATH` values for the server-managed originals and thumbnail stores.
- `powershell.exe` with .NET `System.IO.Compression` support on Windows, or `/usr/bin/ditto` and `/usr/bin/unzip` on macOS, to generate and test the three data ZIPs. The Windows generator uses the .NET ZIP API from PowerShell, not the `Compress-Archive` cmdlet.

No SERVER address, credentials, database, or source paths are bundled. The existing backend backup preflight validates these configured sources and returns actionable errors when any requirement is missing. Package artifacts are staged in the SERVER's private manual-export area and served only through administrator-authenticated endpoints. The Developer frontend itself does not discover or read SERVER filesystem paths. Do not run package generation unless the configured SERVER and its source data are explicitly authorized for this purpose and confirmed non-production.

## Prerequisites and secrets

- Install a currently supported Node.js LTS release from <https://nodejs.org/>.
- Install PostgreSQL 18 or newer client tools, including `pg_restore` and `psql`. Older installed versions are rejected with an upgrade link; the helper does not replace an existing PostgreSQL installation.
- The restored backend's BullMQ thumbnail worker uses Redis at `localhost:6379` by default. The helper does not install, configure, start, or verify Redis; its success checks do not establish background thumbnail-queue readiness. Install/start a local Redis service and verify queue processing separately when that functionality is required.
- Keep the `BACKUP_ENCRYPTION_KEY` used by the source Stocksite backup in a separate, trusted secret store. The website ZIP contains the backup engine's encrypted `.env` payloads, not the key. Do not put production credentials or keys in this ZIP, a browser field, source control, or an email.
- The helper does not invent a PostgreSQL server, database, filesystem destination, or PostgreSQL credential. Supply local PostgreSQL values through the helper's protected environment and select new destinations. If `RESTORE_APP_JWT_SECRET` is blank, the helper generates a cryptographically random local-only secret in memory and writes it only to the restored backend environment file.

## Disposable PostgreSQL 18 integration test

This test is destructive to its target cluster in a narrowly scoped way: it creates and drops uniquely named synthetic databases. Never point it at an application, shared, production, or otherwise valuable PostgreSQL cluster. A loopback address, port 55418, or PostgreSQL 18 version alone does not prove a cluster is dedicated or disposable.

The required local binaries are the PostgreSQL 18 executables under `/opt/homebrew/opt/postgresql@18/bin`: `initdb` (only when an operator provisions a new cluster), `pg_ctl`, `pg_controldata`, `psql`, `pg_dump`, and `pg_restore`. The integration itself executes only `psql`, `pg_dump`, and `pg_restore`; it does not fall back to PATH to find them. It connects only to `127.0.0.1:55418` and does not read the application's database configuration.

Before running the test, an authorized local operator must establish and independently verify all of the following:

1. Use a **separate, disposable PostgreSQL 18 cluster** created specifically for this integration test, with a new dedicated data directory and separate configuration. Do not reuse the Homebrew PostgreSQL service data directory, including an existing PostgreSQL 17 or 18 directory. Configure this test cluster to listen only on IPv4 loopback (`127.0.0.1`) at port `55418`; do not expose it to a network. Keep its Unix socket directory separate as well.
2. Confirm no other process owns port `55418`. Confirm the running process command line points to the dedicated test data directory and that the cluster's `SHOW data_directory`, `SHOW config_file`, `SHOW listen_addresses`, `SHOW port`, and `server_version_num` agree with the intended isolated setup. Check the cluster's control data and service/process identity before connecting. If any identity or isolation detail is uncertain, do not run the test.
3. Create a dedicated login role for this test with `CREATEDB`, but not `SUPERUSER`, using a new local-only password. This role creates and owns the synthetic source/target databases and therefore can drop only those it created. Do not use an application role or a broadly privileged administrator account.
4. Store the role's password in a user-owned PostgreSQL passfile, never in a command argument, shell history, environment value, repository file, or report. Set its permissions to `0600` (or stricter). The entry must be `127.0.0.1:55418:*:<test-role>:<password>`; escape `:` and `\` in the password according to PostgreSQL passfile syntax.
5. Set the two test variables in the current shell without putting a password in either variable:

   ```sh
   export STOCKSITE_PG18_TEST_USER='stocksite_pg18_test'
   export STOCKSITE_PG18_TEST_PGPASSFILE="$HOME/.config/stocksite/pg18-test.pgpass"
   ```

   The username may be another role that satisfies the constraints above. The passfile path must be absolute. The test verifies ownership, regular-file/no-symlink status, restrictive permissions, and a matching non-empty entry; it never prints the file contents and disables password prompts.
6. Reconfirm the exact target cluster and its disposable ownership immediately before running the test. Then, from the repository root, run:

   ```sh
   npm --prefix backend run test:restore-postgres18
   ```

The test generates unique names beneath `stocksite_pg18_restore_it_`, refuses name collisions, validates PostgreSQL 18 binaries and server identity, then makes only synthetic database content. Cleanup drops only databases this run successfully created and whose database comment still matches the run-specific identity marker; the helper end-to-end test also validates the marker before dropping. Cleanup failures are reported rather than silently treated as success. Abrupt termination can leave synthetic databases or temporary files for operator inspection; do not remove any database unless its name and run marker have been independently confirmed.

The integration creates a synthetic custom-format backup and a complete synthetic `STOCKSITE-RESTORE-PACKAGE`, verifies its manifest, SHA-256 inventory, archive TOC, and ZIP inventories, restores to a new empty database, checks synthetic schema and rows, and removes only databases created by that run after verifying their database identity marker. It also exercises the helper's actual validation, extraction, dependency-install/build, service-health, and post-health launch orchestration with isolated synthetic applications. The test does not use a SERVER-generated package, run the real Stocksite application, establish source-schema compatibility, or apply application migrations; those remain separate acceptance gates.

## Windows setup

The current workflow is not a one-click Windows installer. Before starting the helper, a Windows user must:

1. Use supported 64-bit Windows 11 desktop build 26200 or newer (25H2+) and x64 Node.js 22+ on an active or maintenance LTS line. The minimum build is intentionally conservative: Microsoft's Windows 11 release lifecycle lists current, supported releases at build 26200+ as of October 2026. Install Node.js from <https://nodejs.org/en/download> and PostgreSQL 18+ Server plus `psql` and `pg_restore` from <https://www.postgresql.org/download/windows/>. Keep npm enabled in the Node installer. `pg_dump` is reported but is not needed to restore. Windows 10, Windows Server, older Windows builds, ARM Node, and non-x64 Windows are not accepted by this conservative support check. Installers are never downloaded or launched by the helper.
2. Start the PostgreSQL service in Windows Services. In pgAdmin, create a login role (suggested name `stocksite_local`) with a new local password using **Login/Group Roles → Create → Login/Group Role**. Create a new database (suggested name `stocksite_local`) using **Databases → Create → Database**, and select that role in the **Owner** field. If a name already exists, choose another unused role/database pair. Do not reuse a website login or an existing database. The helper never creates, drops, or alters roles or databases.
3. Download and retain the separate package files in a private folder. Required local restore inputs are `stocksite.backup`, `website-code.zip`, `original-assets.zip`, `thumbnails.zip`, `restore-package-manifest.json`, and `checksums.sha256`. The first four are the separately supplied restore payloads; the signed manifest and checksum list authenticate and inventory them. Download and extract the setup-only `stocksite-restore-helper.zip` separately to a user-owned working folder; keep package originals unchanged.
4. In File Explorer, open the extracted `helper` folder, click its address bar, type `powershell`, and press Enter. Run `npm ci --ignore-scripts`. Copy `.env.example` to `.env` without overwriting any existing file. Generate a random token without displaying it by running `$b=New-Object byte[] 32; $r=[Security.Cryptography.RandomNumberGenerator]::Create(); $r.GetBytes($b); Set-Clipboard ([Convert]::ToBase64String($b)); $r.Dispose(); Write-Host 'Random token copied; paste it only into helper/.env.'`; replace the example `RESTORE_HELPER_TOKEN` value in the private `.env` using Notepad, then clear the clipboard with `Set-Clipboard -Value ''`. Never paste the token into a command, URL, or shared file. Review **Properties → Security** for the helper folder and `.env` and restrict access to your Windows account. The helper does not configure or verify Windows ACLs.
5. Run `start-windows.cmd` and leave its terminal open. Open `http://127.0.0.1:43127/` and enter the helper token. Click **Check this PC**. For missing/unsupported Node/npm, install supported x64 Node.js LTS with npm from the official Node.js page; for missing `psql` or `pg_restore`, install PostgreSQL 18+ and add its command-line tools to `PATH`. Close/reopen PowerShell and the helper, then check again. The helper does not run installers or change PATH.
6. In **Local setup**, enter `127.0.0.1`, the port shown by pgAdmin (normally `5432`), the dedicated role and password, the matching empty database name, and an unused local Stocksite port (suggested `5001`). The form sends the database password only to the authenticated loopback helper, keeps it in memory, and does not write it to helper files, logs, or responses. Enter the independently trusted Ed25519 public key unless it is already configured in `helper/.env`; do not accept a key included only in the package. The helper creates a cryptographically random local-only JWT secret automatically if one is not configured.
7. Select the four package source paths and three new, non-overlapping destination folders. Paths containing spaces are supported. Click **Check this PC** and follow each failed check's next action; after installing tools or starting PostgreSQL, reopen/check again. Validation connects only to the configured loopback host and checks PostgreSQL 18+, role/database ownership, and that the selected database is empty. It does not create or delete database objects.

The helper verifies the package signature using an independently trusted public key, plus the manifest, SHA-256 checksums, archive TOCs, and inventories before installing dependencies or extracting files. Before every consequential restore action, it pauses to show the source, destination, impact, administrator-permission expectation, and separate **Approve**/**Cancel** choices. Approval applies only to the displayed action. It refuses existing destination folders, non-loopback database server addresses, databases not owned by the configured role, and non-empty database targets. **Check this PC** is read-only: it reports supported versions and exact next actions with official download links, but does not install software, start services, create roles/databases, or change Windows permissions. Browsers do not expose native file paths to the helper, so paths are entered and then validated locally.

If failure occurs before the database restore starts and no destination is promoted, the job is `FAILED` or `CANCELLED`; only the operation's private temporary staging folders are cleaned up. Once `pg_restore` starts, a later failure/cancellation is reported as `PARTIAL` because the database may be partly or fully restored. If promotion creates destination directories before a later error, the job is also `PARTIAL` and the report lists those operation-created directories. Such database contents or promoted directories are deliberately not deleted automatically. Do not retry into them. Read the failure report, create a new verified empty local database and new destination folders, and retry only after resolving the cause. Inspect or remove existing partial data manually only after independently confirming it is disposable and explicitly choosing to remove it. There is no transactional rollback for PostgreSQL restore or cross-directory promotion.

The Windows readiness policy requires Windows 11 desktop build 26200+ and x64 Node.js 22+ on an active/maintenance LTS line. This floor follows Microsoft's Windows 11 release information (https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information) and is deliberately stricter than the minimum version accepted by Windows itself. Windows 10 Home/Pro ended support in October 2025; older 23H2/24H2 builds and LTSC editions are not accepted by this conservative check. The updated Windows detection and guidance have only been unit-tested with synthetic system/service responses on non-Windows; actual Windows behavior, PowerShell availability, ACL handling, installer compatibility, process-tree shutdown behavior, and full restore acceptance remain untested. The helper terminates only the child process handles it directly created; it does not use PID-based tree killing that could affect an unrelated process after PID reuse.

## Developer macOS setup

1. Extract the helper ZIP to a user-owned folder.
2. Copy `helper/.env.example` to `helper/.env` without overwriting an existing file; set `RESTORE_HELPER_TOKEN` to at least 32 random characters and configure `RESTORE_UI_ORIGIN` only if hosting the UI from the Stocksite admin page.
3. In Terminal, run `npm ci --ignore-scripts` from `helper/` to install the pinned ZIP reader without running package lifecycle scripts. Then run `sh start-macos.sh` or `npm start`. The helper binds only to `127.0.0.1`.
4. Open `http://127.0.0.1:43127/` and enter the token. Keep the helper terminal open during restore.
5. Use **Local setup** to enter the dedicated loopback PostgreSQL role/password/database and independently trusted package public key, then place the separately downloaded database backup and three data ZIPs beside `restore-package-manifest.json` and `checksums.sha256` in one private folder. Enter the four payload paths in the wizard. Before any restore action, the helper checks that each payload is present in that folder, verifies the detached checksum and trusted manifest signature, validates archive paths and contents against the signed inventory, and reports missing or mismatched files with an actionable error. Filesystem access is performed by the helper process running as your logged-in user.

Start scripts are `sh start-macos.sh` on macOS and `start-windows.cmd` on Windows. Alternatively run `node server.js` from the helper folder.

## Manifest trust

The helper checks the SHA-256 digest of its bundled manifest. Restore packages must also carry a valid Ed25519 signature over their canonical manifest. Package generation requires `RESTORE_PACKAGE_SIGNING_PRIVATE_KEY_FILE` to point to a protected server-side private-key file; the restore helper accepts `RESTORE_PACKAGE_SIGNING_PUBLIC_KEY` (base64-encoded Ed25519 SPKI DER) from its local `.env` or the wizard's memory-only Local setup form. Obtain that public key through a trusted channel independent of the package; never trust a key supplied only inside the downloaded package. Missing keys or invalid signatures fail closed before dependency installation or restore actions begin. An optional latest software manifest can be configured using `RESTORE_MANIFEST_URL` and `RESTORE_MANIFEST_PUBLIC_KEY`; it must be HTTPS and carry a valid Ed25519 signature in the `x-restore-manifest-signature` response header.

### Operator key provisioning (not performed by this repository)

Perform these steps only in an authorized key-management environment. Do not generate a replacement key casually on a workstation or put key material in source control, a package, a database, logs, or chat.

1. On a dedicated trusted operator host, create an access-controlled key directory and generate one persistent Ed25519 PKCS#8 private key. On a POSIX host:

   ```sh
   umask 077
   mkdir -m 700 stocksite-restore-signing
   openssl genpkey -algorithm Ed25519 -out stocksite-restore-signing/package-signing-key.pem
   chmod 600 stocksite-restore-signing/package-signing-key.pem
   ```

   On Windows, create the file in an administrator-controlled directory and grant read access only to the package-generation service identity and the minimum required recovery administrators using the Windows Security UI or `icacls`. Do not grant access to `Users` or `Everyone`. The current generator verifies that the key is a regular, non-symlink file and checks POSIX ownership/mode where available; it does not programmatically audit Windows ACLs, so an operator must verify those ACLs before enabling signing.

2. Derive the public key in SPKI DER form and fingerprint it without displaying private material:

   ```sh
   openssl pkey -in stocksite-restore-signing/package-signing-key.pem -pubout -outform DER -out stocksite-restore-signing/package-signing-public.der
   openssl dgst -sha256 stocksite-restore-signing/package-signing-public.der
   openssl base64 -A -in stocksite-restore-signing/package-signing-public.der
   ```

   The SHA-256 digest is the public-key fingerprint. The base64 output (not the PEM wrapper) is the value expected by `RESTORE_PACKAGE_SIGNING_PUBLIC_KEY`. Share both the base64 public key and fingerprint with the helper operator over an authenticated, independently verified channel; compare the fingerprint out-of-band before configuring the helper. Never obtain the trust anchor solely from the package being checked.

3. Place the private key in the package-generator host's protected secret/configuration directory, set `RESTORE_PACKAGE_SIGNING_PRIVATE_KEY_FILE` to its absolute path, and restart only the authorized package-generation service as part of its normal change process. Do not put the private-key contents in an environment variable. Configure the matching public key in the helper's private `.env`, then verify the public fingerprint and run a synthetic sign/verify/tamper test before releasing packages. Missing, malformed, wrong-algorithm, or mismatched keys fail closed; the generator will not start a real package job without a usable private key.

4. Keep a protected, encrypted recovery copy of the private key and record its fingerprint, key ID, creation date, custodian, and rotation date in the organization's approved key inventory. Restrict access, audit retrieval, and test recovery using synthetic material in a non-production environment. Never store the recovery copy with restore packages or backups that it is meant to authenticate.

5. Rotate by preparing a new key pair and distributing its public key independently before signing any package with it. The current helper accepts one configured public key, not a key ring: switching keys makes packages signed by the former key fail verification. Therefore retain old trusted public keys in controlled operator records and use a separately reviewed helper release/configuration that explicitly supports a bounded key ring if old packages must remain restorable. Otherwise, state that old packages are no longer accepted and generate a newly signed package through the normal authorized process. Never respond to a signature failure by disabling verification or trusting a package-supplied key.

## Safety and current limitations

- `restore-package-manifest.json` uses schema version 1 and describes every downloadable artifact, its logical source, package destination, size, SHA-256 (or the documented self-checksum exception), inclusion status, and verification result. It records PostgreSQL server/`pg_dump` versions and dump timestamp without connection credentials or secret contents.
- The manifest's source inventory records each collected file's relative source/destination path, size, checksum, and verification state. Original-assets and thumbnail inventories are included separately by category and retain their relative names. The archive tools stream file contents; inventory metadata is separate from file payload bytes.
- The code exclusion policy is explicit: `.git` metadata/history; `node_modules`; generated build/coverage output; backup state and archives; temporary/cache/log/upload/staging directories; OS metadata (`.DS_Store`, `Thumbs.db`, `desktop.ini`); `dump.rdb`; and root-level content outside the approved Stocksite source/configuration roots. Dependencies are regenerated from included lockfiles. The source package includes applicable setup documentation, startup scripts, package manifests/lockfiles, backend and frontend trees, migrations, tests, public files, and hidden configuration files. Required `.env*` files are encrypted and included only after explicit administrator consent.
- The canonical SHA-256 for `restore-package-manifest.json` is computed with its own checksum fields nulled; `checksums.sha256` includes that canonical checksum. A checksum file cannot contain its own checksum, so its manifest record includes its exact byte size and entry-validation result but has no self-referential digest.
- Create a new, empty PostgreSQL database before starting. Configure `RESTORE_APP_DB_HOST`, `RESTORE_APP_DB_PORT`, `RESTORE_APP_DB_USER`, and (if required by local PostgreSQL) `RESTORE_APP_DB_PASSWORD` in the helper's private `.env`. Database hosts are restricted to `localhost`, `127.0.0.1`, or `::1`; `localhost` is converted to numeric `127.0.0.1` before any database connection to avoid resolver-dependent routing. Remote database targets are rejected.
- Configure a new random `RESTORE_APP_JWT_SECRET` of at least 32 characters and an available `RESTORE_APP_PORT` in the helper's private `.env`. The helper writes `backend/.env` and `frontend/.env.production.local` files for the selected local database and storage destinations, using restrictive file mode where supported. Windows does not honor POSIX file modes; verify NTFS Security permissions on the helper folder and generated environment files. It does not copy or decrypt encrypted source `.env` files.
- Select new, non-overlapping filesystem destination paths. Existing destinations are rejected; the helper does not silently overwrite.
- The database artifact is PostgreSQL custom format (`PGDMP`) and is restored with `pg_restore`; the helper lists its table of contents before restore and verifies the package checksum. A readable TOC is not a guarantee that a restore will succeed.
- `.env` payloads are encrypted at rest in the source backup. This helper does not decrypt or install production secrets. It generates local environment files from the helper's explicitly configured local PostgreSQL settings and selected storage destinations. Never reuse production credentials or signing keys on a new computer.
- The helper rejects unsafe archive paths, duplicate and platform-colliding entries, symlinks and special files, inventory/checksum mismatches, insufficient filesystem space, and changed package artifacts. ZIPs are streamed through the pinned `yauzl` reader, verified per file, and extracted without overwriting existing files. Encrypted `.env` payloads are checksum-verified but skipped; configure local environment values instead. Extraction is staged in private directories and promoted only to new, previously validated destinations.
- Software installers that do not report progress are shown as indeterminate. Package-manager actions are allowlisted in helper code, not supplied by the manifest.
- After restoring the database and staging files, the helper starts `backend/server.js` with `HOST=127.0.0.1`, checks `/health` (which runs a PostgreSQL query), and verifies the built frontend root is served from `/`. It reports `COMPLETED` and exposes the Open Stocksite link only after all checks pass. These checks do not verify sign-in, application features, image/original delivery, or thumbnail processing. A failed health check is a failed restore; already-restored database contents and destination files may require manual cleanup before trying again.
- The helper checks available source-version metadata but cannot establish full database schema compatibility from version labels. It runs a read-only check of the restored application's `checkAssetLifecycleSchema` after restore/build and before promoting files or starting the backend; missing required asset lifecycle tables, columns, indexes, or constraints fail the restore, and this check does not apply migrations. This is not a complete application-schema compatibility proof. The helper does not invoke migration scripts as a restore stage, but launching the restored `backend/server.js` runs its normal `initializeThumbnailSystem()` startup initializer, which executes its individually loaded startup migration sequence (legacy migration files through 027) before requiring the schema from migrations 028, 029, and 030. That initializer does not apply migrations 028–030; have required schema changes applied only through an approved process before launch. Startup may modify the selected local restored database, so review the source/database revisions and use only a disposable local database. Redis-backed thumbnail-queue readiness is not part of the helper's success health check. Restore job state is held in helper-process memory and is lost if the helper is restarted. There is no automatic rollback of a database restore or already-promoted destination folders after a later failure.
- This repository's current acceptance run has not exercised a non-production SERVER package job, a full helper-driven disposable Stocksite restore, or Windows execution. Those are unverified and must not be described as passed.
- The generated package is private and available only through authenticated administrator routes. Treat every download as sensitive; keep it in an access-controlled location and delete it according to your retention policy.
